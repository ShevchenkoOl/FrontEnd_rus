# 📖 Полное руководство: Git, GitHub и командная разработка (Git Flow)

**Git** — это самая популярная распределенная система управления версиями, которая отслеживает изменения в файлах, хранит историю их версий и позволяет возвращаться к ранним состояниям. Это незаменимый инструмент для разработчиков, позволяющий работать над проектом одновременно нескольким людям, не затирая файлы друг друга. 
Говоря простыми словами это программа которая установлена на ваш локальный ПК и помагает отслеживать все изменения вашего кода.
Установить и прочитать более детальную информацию вы можете здесь: [Git](https://git-scm.com/)<br>
**GitHub** — это крупнейший облачный сервис для хостинга IT-проектов и их совместной разработки. Он работает на базе системы контроля версий Git, позволяя разработчикам хранить, редактировать, отслеживать изменения и обмениваться кодом из любой точки мира, работая над проектами как индивидуально, так и в команде.
Проще говоря GitHub это облако (как Google Drive или ICloud), где хранится ваш код. Зерегистрироваться вы можете здесь: [GitHub](https://github.com/)

Давайте пройдем путь от настройки компьютера до профессиональной работы в команде.

## Шаг 1. Представься системе (Глобальные настройки)
После установки git, мы должны убедиться что git действительно успешно установлен и наш ПК его видит, для этого откройте терминал (VS Code, PowerShell или Terminal) и введите:
```bash
git -version
// если git установлен мы получим приблизительно такой ответ
git version 2.44.0.windows.1
// в противном случаи у нас будеи выведена ошибка красного цвета.
```
Прежде чем сохранять код, Git должен знать, кто вы. Это нужно, чтобы в истории проекта было видно, кто именно написал ту или иную строчку.

```bash
git config --global user.name "Твое Имя"
git config --global user.email "email@example.com"
```
Флаг `--global` означает, что эти данные будут использоваться для всех проектов на вашем компьютере. Если для конкретного рабочего проекта нужна другая почта, введите те же команды внутри папки проекта, но без `--global`.

**Как проверить свои настройки:**
```bash
git config --list
# или конкретно:
git config --global user.name
```

**Как «разлогиниться» на чужом компьютере:**
```bash
git config --global --unset user.name
git config --global --unset user.email
```

## Шаг 2. Создание проекта (Два сценария)

### Сценарий А: Репозиторий уже есть на GitHub (Клонирование)
Если капитан команды уже создал проект, вам нужно просто скачать его себе.
1. Копируем ссылку на GitHub (HTTPS или SSH).
2. В терминале пишем:
   ```bash
   git clone <ссылка_на_репозиторий>
   ```
3. Заходим в папку скачанного проекта:
   ```bash
   cd название-проекта
   ```
4. Устанавливаем зависимости (скачиваем библиотеки, например React):
   ```bash
   npm install 
   # (или npm ci / yarn install)
   ```

### Сценарий Б: У вас есть код локально, но нет на GitHub
1. Инициализируем Git в папке с вашим кодом:
   ```bash
   git init
   ```
2. Сохраняем все файлы:
   ```bash
   git add .
   git commit -m "Initial commit"
   ```
3. Идем на GitHub, создаем пустой репозиторий (New Repository). Копируем ссылку.
4. Привязываем локальную папку к GitHub и отправляем код:
   ```bash
   git remote add origin <ссылка_на_репозиторий>
   git branch -M main
   git push -u origin main
   ```

## Шаг 3. Архитектура веток (Git Flow)

После создания нового репозитория (проекта), у вас по умолчанию будет создана только одна ветка `main`.
В профессиональной разработке **никто и никогда не пишет код напрямую в ветку `main`**.
Мы в ручную создаём ветку `develop`:
```bash
git checkout -b develop
```
а от нее создаём ветку для новой задачи, например: `faature/layout-footer&header`
Представьте себе завод:
* 👑 **`main` (Витрина):** Здесь лежит только идеальный, протестированный код. Отсюда код попадает к реальным пользователям на боевой сайт.
* 🛠 **`develop` (Мастерская):** Здесь собираются все новые фишки от всех разработчиков для тестирования.
* 📝 **`feature/...` (Ваш рабочий стол):** Ветка для одной конкретной задачи.

**Как правильно создать ветку для новой задачи:**
Убедитесь, что вы находитесь в ветке `develop`, обновите её и создайте свою:
```bash
git checkout develop                          // переходим в ветку develop
git pull origin develop                       // обновляем ветку develop
git checkout -b feature/ITDEV-123-login-form  // создаём новую ветку под названием feature/ITDEV-123-login-form
```
*Разбор названия `feature/ITDEV-123-login-form`:*
* `feature/` — тип (еще бывает `bugfix/` — исправление ошибки).
* `ITDEV-123` — номер задачи в трекере (Jira, Trello).
* `login-form` — коротко о том, что вы делаете.

## Шаг 4. Ежедневная рутина (Пишем код и сохраняем)

Вы написали код формы логина. Пора его сохранить.

1. **Проверка статуса** (Ваша главная команда, делайте её всегда!):
   ```bash
   git status
   ```
2. **Добавляем файлы** на «сцену» (готовим к сохранению):
   ```bash
   git add . 
   # (или конкретный файл: git add index.html)
   ```
3. **Фиксируем** изменения с понятным комментарием:
   ```bash
   git commit -m "ITDEV-123: Добавлена логика авторизации"
   ```
4. **Отправляем** ветку на GitHub (флаг `-u` нужен только в самый первый раз для новой ветки):
   ```bash
   git push -u origin feature/ITDEV-123-login-form
   ```

## Шаг 5. Pull Request и Code Review

Ваша задача готова локально и отправлена на GitHub. Теперь её нужно объединить с общим кодом.

1. Зайдите на GitHub. Появится зеленая кнопка **"Compare & pull request"** — жмите её!
2. Внимательно проверьте направление: **base: `develop` <- compare: `feature/...`** *(Мы несем код в develop, не в main!)*.
3. Опишите, что вы сделали, и назначьте коллег для проверки (Reviewers).
4. Нажмите **Create pull request**.

### Что делать, если коллеги попросили что-то исправить (Code Review)?
Вам **НЕ нужно** создавать новую ветку или новый Pull Request!
1. Откройте проект в VS Code и убедитесь, что вы в своей рабочей ветке (`git branch`).
2. Внесите нужные правки в код.
3. Сохраните и отправьте:
   ```bash
   git add .
   git commit -m "fix: исправил замечания по ревью"
   git push
   ```
*Магия GitHub:* Ваш новый коммит автоматически подгрузится в уже открытый Pull Request!

## Шаг 6. Слияние (Merge)

Когда ваш код одобрен, его пора влить в `develop`. В самом низу вашего Pull Request есть зеленая кнопка. У нее есть несколько режимов:

* 🥇 **Squash and merge (Рекомендуемый стандарт!)**
  Берет все ваши 15 мелких коммитов (вроде *"поправил опечатку"*, *"забыл запятую"*) и «сплющивает» их в один большой, красивый коммит. История проекта остается идеально чистой.
* 🥈 **Create a merge commit (Обычный)**
  Переносит всю историю ваших мучений. В истории главной ветки начнется каша из мелких коммитов всей команды.

После успешного слияния (Squash and merge), ветку на GitHub можно удалить.
А на своем компьютере сделайте следующее:
```bash
git checkout develop
git pull origin develop
git branch -D feature/ITDEV-123-login-form  # Удаляем отработавшую ветку локально
```

## 🛡 Продвинутые настройки: Защита и Хостинг

### 1. Защита ветки `main` (Branch Protection)
Чтобы никто случайно не сломал продакшн, заблокируйте прямую запись в `main`.
* GitHub -> Settings -> Branches -> Add classic branch protection rule.
* Впишите `main`. Поставьте галочки **Require a pull request before merging** и **Do not allow bypassing the above settings**.
* *Примечание:* Бесплатно работает только для Public-репозиториев. Для Private потребуется дисциплина команды.

### 2. Настройка Netlify (Деплой)
Чтобы клиенты видели боевой сайт, а вы могли тестировать ветку `develop`:
* Зайдите в Netlify -> Site configuration -> Build & deploy.
* **Production branch:** Убедитесь, что там стоит `main`.
* **Branch deploys:** Выберите *Let me add individual branches* и впишите `develop`.
* **Deploy Previews:** Включите для проверки каждого Pull Request.

## 🆘 Скорая помощь: Если что-то пошло не так

**Как переименовать ветку?**
*Если она еще НЕ отправлена на GitHub:*
```bash
git branch -m <новое_имя>
```
*Если она УЖЕ на GitHub (нужно 3 шага):*
```bash
git branch -m <новое_имя>
git push origin -u <новое_имя>
git push origin --delete <старое_имя>
```

**Терминал просит пароль от GitHub, а мой пароль не подходит?**
GitHub больше не принимает обычные пароли в терминале. Вам нужен **Token**.
* GitHub -> Settings -> Developer settings -> Personal access tokens (classic) -> Generate new token.
* Отметьте галочку `repo`.
* Скопируйте длинный код (он покажется только один раз!) и вставьте его в терминал вместо пароля.

## ⚔️ Решение конфликтов (Merge Conflicts)

Для новичков слово «конфликт» звучит страшно, но на деле это абсолютно нормальная и ежедневная часть командной разработки.

**Что такое конфликт?**
Представьте, что вы и ваш коллега взяли один и тот же файл (например, `index.html`) и одновременно изменили 15-ю строчку. Когда вы попытаетесь слить свои изменения вместе, Git поднимет руки вверх и скажет: *«Ребята, я робот, я не знаю, чей код важнее. Решите сами!»*.

Обычно это происходит во время команд `git pull`, `git merge` или при попытке слить Pull Request на GitHub.

**Алгоритм спасения (без паники):**

**1. Прочитайте сообщение Git**
Когда возникает конфликт, терминал напишет что-то вроде:
`CONFLICT (content): Merge conflict in index.html`.
Это значит, что Git остановил процесс слияния, и теперь вы находитесь в «режиме разрешения конфликта».

**2. Откройте VS Code**
Решать конфликты в терминале — это боль. Откройте конфликтующий файл (в нашем примере `index.html`) в VS Code. Редактор подсветит проблемный участок яркими цветами и добавит странные маркеры:

```html
<<<<<<< HEAD (Current Change - То, что сейчас в вашей ветке)
<h1>Привет, мир!</h1>
=======
<h1>Привет, пользователи!</h1>
>>>>>>> feature/new-title (Incoming Change - То, что прилетело от коллеги)
```

**3. Сделайте выбор**
Прямо над этим блоком VS Code любезно предложит вам удобные кликабельные кнопки:
* **Accept Current Change** — оставить ваш вариант (удалить код коллеги).
* **Accept Incoming Change** — взять вариант коллеги (удалить ваш).
* **Accept Both Changes** — оставить обе строчки (часто нужно, когда вы добавили новый CSS-класс, а коллега — другой).

Нажмите нужную кнопку (или просто удалите маркеры `<<<<<<<`, `=======`, `>>>>>>>` и отредактируйте код руками так, как считаете нужным).

**4. Завершите слияние**
Как только вы очистили файл от конфликтов и сохранили его (Ctrl+S / Cmd+S), нужно сказать Git, что проблема официально решена:

```bash
# 1. Говорим Git, что конфликт улажен
git add .

# 2. Делаем коммит, фиксирующий решение
git commit -m "fix: resolve merge conflicts in index.html"

# 3. Отправляем обновленный код на сервер
git push
```

🎉 Всё! Конфликт решен, вы великолепны, и ваш код снова в безопасности.
